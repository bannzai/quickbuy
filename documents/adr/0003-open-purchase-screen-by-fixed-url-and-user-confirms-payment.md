# 0003. 購入画面は決まった形の URL で開き、支払いの確定は毎回本人が行う

## Status
Accepted (2026-11-17)

## Context
Quick Buy は「自分で決めるが、決めた後は 1 タップ」を狙う (企画: https://github.com/bannzai/IdeaMemo/issues/398 の「欲求」)。カートに商品を入れる方法には、店や EC サイトが用意した URL を開く方法と、アプリの中で EC サイトにログインさせてブラウザを自動で操作する方法がある。企画は後者を「採らない方式」としている。理由は、ログイン情報を預かる責任が重いこと、画面の変更や認証で壊れること、ウィジェットから裏で動かせないこと。

また、URL を保存して開くアプリは、外から渡された URL をそのまま開くと、任意のサイトへ利用者を送る踏み台になる。

## Decision
- アプリは購入を完了させない。商品がカートに入った状態の購入画面を開くところまでを行い、支払いの確定は毎回、本人が店・EC サイトの画面で行う
- EC サイトのログイン情報を預からない。アプリの中でログインさせてブラウザを自動で操作する方式を採らない
- 購入画面の URL は、アプリ (サーバーを持つ段階ではサーバー) が決まった形で組み立てる。外から渡された URL (店が配るリンク・QR、共有された文字列) は、店のドメイン・商品の識別子・個数に分解してから組み立て直し、そのまま開かない。URL に入れるのは店のドメイン・商品の識別子・個数と、形式が決めている付帯の値 (流入元を示す値等) だけにする
- 決まった形で組み立てることが限るのは、URL のパス (商品の識別子と個数) だけで、店のドメインは限らない。組み立ての関数 (`Shared/ShopifyCartPermalink.swift`) はドメインの形だけを検査し、どの店かは見ない (Shopify の店は独自ドメインを使えるため、許可する店の一覧を持てない)。店のドメインを信頼する根拠は、お気に入りを登録する時に置く: 登録の画面で店のドメインを利用者に見せ、利用者が自分で確かめて登録の操作をしたものだけを保存する。外から渡されたリンク (店が配る追加リンク・QR、共有された URL) は、この確認の画面を通さずに保存せず、開かない。購入画面を開けるのは、保存済みのお気に入りからだけにする
- 登録の時に、そのドメインが Shopify の店であることを機械的に確かめるかは未決定。お気に入りの登録を実装する issue で決め、この ADR に追記する
- 決済の URL のうち、提供元が本人以外への共有とログへの記録を禁じているもの (Shopify の Checkout MCP の `continue_url`。出典: https://shopify.dev/docs/agents/checkout/mcp ) は、通知・ログ・計測のイベントに載せない

## Consequences

**良い点:**
- 知らないうちに購入されることが無く、「買う時は自分で決めたい」という対象の人の条件を満たす
- ログイン情報を持たないため、漏えい時の被害と、EC サイトの規約・法務上のリスクを避けられる
- 開く URL のパスが決まった形に限られ、開く先のドメインは利用者が登録の時に確かめたものに限られるため、外から渡されたリンクだけで任意のサイトへ送られることが無い

**悪い点 / 引き受けるリスク:**
- 利用者が登録の画面でドメインを確かめずに登録すると、店を装ったドメインの購入画面が開く。登録の画面でドメインを目立つ形で見せることを、お気に入りの登録の実装の完了条件に入れる
- カートに入れる URL を公式に用意していない EC サイト (企画の時点では楽天) は、商品ページを開くところまでになる
- URL の形式は提供元の変更で使えなくなることがある (Amazon のカートに入れる URL は公式ドキュメントが無い。企画の「Amazon: カートに入れる URL」)。形式ごとに組み立ての関数とテストを 1 か所に置き、変更に 1 か所で追随する
