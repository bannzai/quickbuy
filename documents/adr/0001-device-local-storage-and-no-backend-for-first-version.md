# 0001. 最初の版はお気に入りを端末内に持ち、サーバーとログインを持たない

## Status
Accepted (2026-11-17)

## Context
Quick Buy は、Shopify の店と Amazon の「いつもの商品」をお気に入りにし、ホーム画面のウィジェットから購入画面を開くアプリ (企画: https://github.com/bannzai/IdeaMemo/issues/398 )。企画の「最初に作る範囲」は次の順になっている。

1. Shopify の Catalog の API キーを発行し、日本の店の商品が検索に出るかを試す
2. iOS で、お気に入り → ウィジェットのタップ → 購入画面、の流れを通す。最初は店の cart permalink と Amazon のカートに入れる URL を保存して開く形にする
3. 自分のサーバーを経由する URL と、店ごとの「いつものセット」を足す
4. 店向けの無料 Shopify アプリを作る

決めるべきは、DB・ストレージ・ホスティング・認証・計測の構成。2 の時点で扱うデータは、利用者が自分で選んだ商品の一覧だけで、利用者どうしの共有もサーバー側の処理も無い。

## Decision
- **DB / ストレージ**: 最初の版 (上の 2) は、お気に入りを端末内にだけ保存する。ウィジェット拡張がアプリと同じデータを読むため、保存先は App Group の共有領域にする。サーバーの DB・クラウドのストレージは持たない
- **ホスティング / バックエンド**: 最初の版は持たない。紹介ページと法務ページだけを GitHub Pages (`docs/`) で配信する。自分のサーバーを経由する URL (上の 3) を作る時に、ホスティングと DB を別の ADR で決める
- **認証**: 最初の版は持たない (ログイン・会員登録の画面を作らない)。サーバーが利用者ごとの商品の一覧を持つ段階で、利用者の識別方法を別の ADR で決める
- **課金**: 消費者向けアプリは無料で、アプリ内課金を持たない (企画の「収益」)
- **計測とクラッシュ収集**: Firebase Analytics と Crashlytics を使う。判定基準の指標を bannzai/dashboard 経由で他のプロダクトと同じ形で読むため (`~/.claude/documents/rules/scaffold-scope-and-product-lessons.md`「雛形にしてよいもの」)。Firebase のプロジェクトの作成は、作るかの判断 (https://github.com/bannzai/quickbuy の「作るかの判断」の issue) の返答の後に行う

## Consequences

**良い点:**
- サーバーの運用・認証・個人情報の扱いが最初の版に無く、ウィジェットから購入画面までの流れの検証に集中できる
- お気に入りが端末の外に出ないことを、最初の版のプライバシーポリシーに書ける

**悪い点 / 引き受けるリスク:**
- 端末の変更・アプリの削除でお気に入りが消える
- URL を端末に保存する形では、URL を変えずに中身の商品を後から足す・減らすこと (店ごとの「いつものセット」) と、経由した回数をサーバーで数えることができない。上の 3 で足す
- 上の 3 でサーバーにお気に入りを移す時に、端末内のデータからの移行が要る
